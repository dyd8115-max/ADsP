# 분석 과제 발굴

> 2과목 데이터 분석 기획 › 1장 데이터 분석 기획의 이해

---

## 분석 과제 발굴

| 개념 | 정의 |
|---|---|
| **분석 과제 발굴** | 해결해야 할 **기업의 문제를 데이터 분석 문제로 변환**하는 개념 |

| 항목 | 설명 |
|---|---|
| **산출물** | 분석 과제는 관계자들이 이해할 수 있도록 **과제 정의서 형태로 도출** |
| **탐색 방식** | 크게 **하향식(Top-Down)**과 **상향식(Bottom-Up)** 두 가지로 나뉨 |

---

## 두 가지 접근법

| 구분 | 하향식 접근법<br>(Top-Down Approach) | 상향식 접근법<br>(Bottom-Up Approach) |
|---|---|---|
| **정의** | 문제가 주어졌을 때 우리가 해결해 나갈 **과제가 무엇인지를 찾는** 전통적 방식 | 다양한 **데이터의 조합 속에서 인사이트를 찾아내는** 방식 |
| **적용 상황** | **분석 대상을 알고 있을 때** | **분석 대상을 모를 때** |
| **배경** | 문제가 명확히 정의되어 있음 | 대규모 데이터가 생성되고 빠르게 변화하여<br>**문제를 사전에 정의하기 어려움** |
| **특징** | 각 과정이 **체계적으로 단계화**되어 문제를 해결 | 데이터 자체에서 출발해 패턴과 의미를 발견 |

> **실무 적용**: 실제 분석 과정에서는 하향식과 상향식을 **혼용해서 많이 사용**한다.

# 하향식 접근법 (Top-Down Approach)

하향식 접근법은 **현황 분석을 통해서나 인식된 문제로부터** 기회나 문제를 탐색하고, 문제를 정의하고, 해결 방안을 탐색하고, 데이터 분석의 타당성을 평가하는 과정을 거쳐 분석 과제를 도출한다.

### 4단계 프로세스 요약

| 단계 | 명칭 | 핵심 활동 |
|---|---|---|
| **1단계** | 문제 탐색 (Problem Discovery) | 기회나 문제를 **발굴** |
| **2단계** | 문제 정의 (Problem Definition) | 비즈니스 문제를 **데이터 분석 문제로 변환** |
| **3단계** | 해결방안 탐색 (Solution Search) | 해결 방안 모색 + **시스템·역량 확인** |
| **4단계** | 타당성 검토 (Feasibility Study) | 경제적 / 데이터·기술적 **타당성 평가** |

---

## 1단계 — 문제 탐색

문제 탐색에는 세 가지 방법이 있다.

---

### 1️⃣ 비즈니스 모델 캔버스 기반 문제 탐색

**비즈니스 모델 캔버스의 9가지 블록을 5가지로 단순화**한 탐색 기법이다.

| 영역 | 구분 | 설명 |
|---|---|---|
| **업무 (Operation)** | 문제 발굴 영역 | 제품·서비스를 생산하기 위한 내부 프로세스 |
| **제품 (Product)** | 문제 발굴 영역 | 생산되는 제품·서비스 자체의 개선 |
| **고객 (Customer)** | 문제 발굴 영역 | 제품·서비스를 사용하는 고객 및 채널 |
| **규제와 감사 (Audit & Regulation)** | 추가 도출 영역 | 업무 활동을 관리·감독하는 규제와 감사 관점 |
| **지원 인프라 (IT & Human Resource)** | 추가 도출 영역 | **분석을 수행하는 시스템 영역**과<br>**이를 운영·관리하는 인력의 영역** |

> **핵심**: 업무·제품·고객 단위로 문제를 발굴하고, 이를 관리하는 **규제와 감사 / 지원 인프라** 두 영역에 대한 기회를 추가로 도출한다.

---

### 2️⃣ 분석 기회 발굴 범위의 확장

기업과 산업 환경을 중심으로 **4가지 영역**에 대해 비즈니스 문제를 발굴하는 방법이다.

| 영역 | 탐색 관점 |
|---|---|
| **거시적 관점** | 문제 혹은 변화가 **기업에 주는 영향**을 탐색 |
| **경쟁자 확대 관점** | 기업에 **위협이 될 상황**을 탐색 |
| **시장의 니즈 탐색** | **시장의 니즈** 관점에서 문제를 탐색 |
| **역량의 재해석** | 역량의 재해석 관점에서 **다시 기업 내부**를 둘러봄 |

> **방향성**: 거시환경 → 경쟁자 → 시장 → 내부 역량 순으로, **외부에서 내부로** 시선을 좁혀 간다.

**세부 관점** ⭐

| 영역 | 세부 관점 |
|---|---|
| 거시적 관점 | 사회, 기술, 경제, 환경, 정치 (STEEP) |
| 경쟁자 확대 관점 | 대체재, 경쟁자, 신규 진입자 |
| 시장의 니즈 탐색 | 고객, 채널, 영향자들 |
| 역량의 재해석 | 내부 역량, 파트너와 네트워크 |

---

### 3️⃣ 외부 참조 모델 기반 문제 탐색

| 항목 | 설명 |
|---|---|
| **기본 개념** | **유사·동종 업계**에서 기존에 수행한 문제 탐색 및 분석 과제 등을 활용 |
| **벤치마킹** | 산업·서비스별 **분석 테마 후보 그룹**을 통해<br>가장 빠르고 쉽게 분석 기회 아이디어를 얻는 방식 |
| **활용 기법** | **브레인스토밍** |
| **결과 처리** | 발견된 문제들은 세부 과제로 도출하기 전에<br>먼저 **분석 유스케이스로 정의** |

> **분석 유스케이스**: 문제에 대한 상세 설명 및 해결 시 효과를 명시해, 향후 데이터 분석 문제로의 전환과 적합성 평가에 활용한다.

---

## 2단계 — 문제 정의

| 항목 | 설명 |
|---|---|
| **정의** | 식별된 **비즈니스 문제를 데이터의 문제로 변환**하여 정의하는 단계 |
| **목적** | 문제를 달성하는 데 필요한 **데이터 및 기법을 정의**하기 위해 데이터 분석 문제로 변환 |
| **관점** | 데이터 분석 문제의 정의는 **최종 사용자(User)의 관점**에서 이루어져야 함 |

### 문제 정의의 예시

| 구분 | 내용 |
|---|---|
| **비즈니스 문제** | "고객들의 불만이 높다" |
| **↓ 변환** | |
| **데이터 분석 문제** | 고객의 불만에 영향을 끼치는 요인이 무엇인지 분석하고,<br>그 요인과 불만율에 대한 **상관 및 예측 모델을 수립** |

> **핵심**: 막연한 비즈니스 언어를 **측정 가능한 분석 언어**로 바꾸는 것이 문제 정의다.

---

## 3단계 — 해결방안 탐색

| 항목 | 설명 |
|---|---|
| **정의** | 문제 정의 단계에서 정의된 문제를 **해결하기 위한 방안을 모색**하는 단계 |
| **동시 검토 사항** | 현재 기업 수준에서 **분석이 가능한 시스템을 갖추었는지**<br>분석을 수행할 **인력이 확보되었는지** 함께 따져봐야 함 |

### 해결방안 탐색 매트릭스

**기존 시스템으로 가능한지**와 **기업 자체의 분석 역량이 있는지**를 판단하여 4개의 해결방안 중 하나를 선정한다.

| | **분석 역량 있음 (O)** | **분석 역량 없음 (X)** |
|---|---|---|
| **기존 시스템으로 가능 (O)** | **기존 시스템과 인력으로 수행** | **역량 확보** (교육, 채용) |
| **기존 시스템으로 불가능 (X)** | **시스템 고도화** | **전문업체 아웃소싱** |

> **판단 순서**: 시스템 가능 여부 → 역량 보유 여부 → 4개 방안 중 선택

---

## 4단계 — 타당성 검토

| 항목 | 설명 |
|---|---|
| **정의** | 수행되어야 할 분석 과제가 정의되고 **어떠한 방법과 인력이 수반될지 결정되었을 때**,<br>해결 방안이 타당한지를 검토 |
| **유형** | 크게 **경제적 타당성**과 **데이터 및 기술적 타당성** 두 가지 |

### 타당성 검토의 두 가지 유형

| 유형 | 검토 내용 |
|---|---|
| **경제적 타당성** | **지출 항목**: 데이터, 시스템, 인력, 유지보수 등의 비용<br>**기대 편익**: 분석 결과 적용 시 추정되는 실질적 비용 절감, 추가 매출, 수익 등<br>→ **분석 비용이 경제적 이득보다 크면 기업에는 손해** |
| **데이터 및 기술적 타당성** | 경제적 가치가 뛰어나도 **분석의 수행 가능 여부**를 따져봐야 함<br>수행될 수 없는 분석을 추진하는 것 역시 경제적 손실<br>**검토 항목**: ① 데이터 존재 여부 ② 분석 시스템 환경 ③ 분석 역량 |

> **핵심**: 경제적 타당성은 "**할 가치가 있는가**", 데이터·기술적 타당성은 "**할 수 있는가**"를 묻는다. 둘 다 통과해야 실제 과제로 전환된다.

# 상향식 접근법 (Bottom-Up Approach)

문제 정의가 어려운 상황에서 **데이터 자체를 탐색**하며 새로운 인사이트를 발견하는 방식이다.

### 핵심 기법

| 기법 | 설명 |
|---|---|
| **비지도학습**<br>(Unsupervised Learning) | 정답(목적변수) 없이 **데이터 자체의 패턴과 구조를 발견**<br>군집분석, 연관분석, 주성분분석 등 |
| **프로토타이핑**<br>(Prototyping) | 일단 **먼저 시도해보고 결과를 확인**하며 개선해 나가는 접근<br>문제 정의가 불명확하고 데이터가 준비되지 않았을 때 유용 |
| **디자인 씽킹**<br>(Design Thinking) | 공감을 바탕으로 발산과 수렴을 반복하며 아이디어를 도출 |

---

### 지도학습 vs 비지도학습

| 구분 | 지도학습 (Supervised) | 비지도학습 (Unsupervised) |
|---|---|---|
| **정답(레이블)** | 있음 | 없음 |
| **목적** | 명확한 **답을 예측·분류** | 데이터의 **숨겨진 패턴 발견** |
| **접근법** | 하향식에 가까움 | **상향식의 핵심 기법** |
| **대표 기법** | 회귀분석, 분류(의사결정나무 등) | 군집분석, 연관분석, 주성분분석 |

---

### 프로토타이핑 접근법이 필요한 경우

| 상황 | 설명 |
|---|---|
| **문제 정의가 어려울 때** | 무엇을 분석해야 할지 명확하지 않음 |
| **데이터가 없을 때** | 필요한 데이터의 존재 여부가 불확실함 |
| **사용자 요구가 불명확할 때** | 일단 결과를 보여줘야 요구사항이 구체화됨 |

```
시행착오 → 결과 확인 → 개선 → 반복
```

> **핵심**: 프로토타이핑은 "**일단 해보고 배운다(Learning by Doing)**"는 철학에 기반한다.

## 디자인 씽킹 (Design Thinking)

### 1️⃣ IDEO 사의 디자인 씽킹 — 더블 다이아몬드 프로세스

| 항목 | 설명 |
|---|---|
| **프로세스 구분** | 크게 **문제 발견 영역**과 **솔루션 제시 영역**으로 구분 |
| **명칭** | 다이아몬드 모양이 두 번 반복되어 **더블 다이아몬드 프로세스**라 불림 |
| **핵심 구조** | **상향식 접근법의 발산 단계**와 **하향식 접근법의 수렴 단계**가<br>반복적으로 수행되어 상호 보완적으로 분석의 가치를 높이는 의사결정 방식 |
| **작동 방식** | **수렴과 발산을 반복**하면서 아이디어를 도출 |

```
   문제 발견 영역            솔루션 제시 영역
  ◇──────────◇          ◇──────────◇
발산      수렴          발산      수렴
(상향식)  (하향식)      (상향식)  (하향식)
```

| 단계 | 사고 방식 | 대응 접근법 |
|---|---|---|
| **발산 (Diverge)** | 가능한 많은 아이디어와 가능성을 펼침 | **상향식** |
| **수렴 (Converge)** | 펼친 것 중 핵심을 선별하고 정의 | **하향식** |

> **핵심**: 디자인 씽킹은 상향식과 하향식이 **한 프로세스 안에서 결합**된 대표적 사례다.

---

### 2️⃣ d.school의 디자인 씽킹 — 5단계 프로세스

**스탠퍼드 d.school**의 디자인 씽킹은 **상향식 접근법 중 하나**다.

| 단계 | 명칭 | 내용 |
|---|---|---|
| **1** | **공감** (Empathize) | 사용자를 관찰하고 그들의 입장에서 문제를 느낌 |
| **2** | **문제 정의** (Define) | 공감을 통해 파악한 니즈를 명확한 문제로 정의 |
| **3** | **아이디어 도출** (Ideate) | 브레인스토밍으로 다양한 해결 아이디어 발산 |
| **4** | **프로토타입** (Prototype) | 아이디어를 빠르게 시제품·모형으로 구현 |
| **5** | **테스트 · 평가** (Test) | 사용자에게 적용해보고 피드백을 받아 개선 |

```
공감 → 문제 정의 → 아이디어 도출 → 프로토타입 → 테스트·평가
  ↑                                              │
  └──────────────── 반복 개선 ────────────────────┘
```

> **핵심**: **공감(Empathize)에서 출발**한다는 점이 하향식과 결정적으로 다르다. 문제를 먼저 정의하지 않고, 사용자를 관찰하며 문제를 발견해 나간다.

---

## 하향식 vs 상향식 요약

| 구분 | 하향식 | 상향식 |
|---|---|---|
| **출발점** | 문제 | 데이터 (또는 사용자 공감) |
| **분석 대상** | 알고 있음 | 모름 |
| **프로세스** | 문제 탐색 → 문제 정의 → 해결방안 탐색 → 타당성 검토 | 데이터 탐색 → 패턴 발견 → 인사이트 도출 |
| **주요 기법** | 비즈니스 모델 캔버스, 외부 참조 모델, 벤치마킹 | 비지도학습, 프로토타이핑, 디자인 씽킹 |
| **사고 방식** | 논리적 · **연역적** | 탐색적 · **귀납적** |
| **다이아몬드 대응** | **수렴** | **발산** |

> **결론**: 하향식은 "**답을 찾는 과정**", 상향식은 "**질문을 찾는 과정**"에 가깝다. 실무에서는 디자인 씽킹처럼 두 방식을 상호 보완적으로 활용한다.

## 상향식 접근법 보충 ⭐

| 항목 | 내용 |
|---|---|
| 관점 전환 | "왜 해야 하는가(Why)"에서 "사물 그대로를 인식하는 무엇(What)"의 관점으로 |
| 비지도 학습 예 | 장바구니 분석, 군집 분석, 기술 통계, 프로파일링 |
| 데이터 활용 | 데이터 자체에서 연관성·패턴을 찾아 문제를 재정의 |

### 프로토타이핑 접근법

**프로세스**: 가설 생성 → 디자인에 대한 실험 → 실제 환경에서 테스트 → 테스트 결과에서 통찰 도출 및 가설 확인

**필요성 3가지** (교재 표현)

| 필요성 | 내용 |
|---|---|
| 문제에 대한 인식 수준 | 문제 정의가 불명확하거나 새로운 문제일 때 — 프로토타입으로 사용자가 원하는 바를 구체화 |
| 필요 데이터 존재 여부의 불확실성 | 필요한 데이터가 있는지 불확실할 때 — 대체 데이터 활용 등을 사전에 확인 |
| 데이터 사용 목적의 가변성 | 기존 데이터의 정의를 재검토해 **사용 목적과 범위를 확대**할 수 있음 |

# 분석 과제 정의서 ⭐

하향식·상향식으로 도출된 과제는 **과제 정의서**로 정리해 프로젝트 수행 계획의 입력물로 쓴다.

| 항목 | 내용 |
|---|---|
| 분석명 | 과제 이름 |
| 분석 정의 | 무엇을 분석하는지 |
| 필요 데이터 | 데이터 소스, 유형, 내부·외부 여부 |
| 분석 방법 | 적용할 기법 |
| 데이터 입수 및 분석 난이도 | 확보·분석이 얼마나 어려운지 |
| 분석 수행 주기 | 일·주·월 단위 등 |
| 분석 결과 검증 오너십 | 결과를 누가 검증할지 |
| 상세 분석 과정 | 분석 절차 |
